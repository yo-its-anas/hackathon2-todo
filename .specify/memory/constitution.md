# Todo App - Spec-Driven Development Constitution

## Core Principles

### I. Spec-Driven Lifecycle (NON-NEGOTIABLE)

The development lifecycle MUST follow this strict order without exception:

1. **Constitution** → Project principles and governance
2. **Specify** → Feature requirements and acceptance criteria
3. **Plan** → Architecture decisions and design
4. **Tasks** → Testable, traceable implementation tasks
5. **Implement** → Code generation via `/sp.implement` only

**Rationale**: This hierarchy ensures that all implementation is grounded in validated requirements and architecture, preventing scope creep, wasted effort, and misalignment with project goals. Each phase builds on the previous with explicit validation gates.

**Enforcement**: No phase may be skipped. If requirements are unclear at any phase, execution MUST halt and clarification MUST be requested before proceeding.

### II. No Code Without Authorization (NON-NEGOTIABLE)

No code may be written unless explicitly authorized by `specs/<feature>/tasks.md`.

**Rules**:
- Every code file MUST map back to a specific task ID
- Every task MUST map back to the implementation plan
- Every plan MUST map back to the feature specification
- Unauthorized code generation is a violation of this constitution

**Rationale**: Prevents feature creep, ensures traceability, and maintains alignment between requirements and implementation. All code must serve a documented purpose.

### III. AI-Only Implementation (NON-NEGOTIABLE)

Manual coding by humans is strictly forbidden. All code MUST be generated by Claude Code via the `/sp.implement` command.

**Rules**:
- Humans may specify requirements, review code, and approve plans
- Humans MUST NOT write implementation code directly
- All code generation MUST go through the `/sp.implement` workflow
- Code reviews validate adherence to specification, not hand-edit code

**Rationale**: Ensures consistency, maintains traceability to specifications, and leverages AI capabilities for implementation while humans focus on requirements, architecture, and validation.

### IV. Clarification Over Assumptions (NON-NEGOTIABLE)

If requirements are unclear or underspecified, execution MUST STOP and clarification MUST be requested. Guessing or making assumptions is forbidden.

**Rules**:
- Use `AskUserQuestion` tool when requirements are ambiguous
- Document all clarifications in the relevant artifact (spec, plan, or tasks)
- Mark unclear items as `[NEEDS CLARIFICATION: specific question]`
- Never proceed with implementation of unclear requirements

**Rationale**: Prevents wasted effort on incorrect implementations. It is always cheaper to clarify upfront than to rebuild after discovering misalignment.

### V. Clean Code Standards (MANDATORY)

All code MUST follow clean code principles with clear separation of concerns and readable structure.

**Rules**:
- Single Responsibility Principle: Each module/class/function has one clear purpose
- Clear naming: Variables, functions, and classes use descriptive, intention-revealing names
- DRY (Don't Repeat Yourself): No code duplication without explicit justification
- Separation of concerns: Business logic, data access, presentation clearly separated
- Minimal complexity: Prefer simple solutions; justify any necessary complexity
- Code comments only where logic is non-obvious; prefer self-documenting code

**Rationale**: Clean code reduces bugs, improves maintainability, enables faster onboarding, and makes AI-generated code more reliable and reviewable.

### VI. Technology Stack Adherence (NON-NEGOTIABLE)

The technology stack MUST strictly follow the phase requirements defined in the official Hackathon II specification.

**Rules**:
- Technology choices MUST be explicitly documented in `specs/<feature>/plan.md`
- Deviations from Hackathon II requirements are forbidden without explicit approval
- All dependencies MUST be justified and documented
- Stack decisions are binding once approved in the plan phase

**Rationale**: Ensures consistency across the project, maintains compliance with hackathon requirements, and prevents architectural drift.

**Note**: For this project, refer to the Hackathon II phase requirements for technology constraints.

### VII. State Management Discipline (MANDATORY)

State management strategy MUST be explicitly defined and consistently applied.

**Rules**:
- Default: In-memory state only
- Persistence: Only add if explicitly required by the feature specification
- State location MUST be documented in `specs/<feature>/plan.md`
- State transitions MUST be traceable and testable
- No hidden or implicit state

**Rationale**: Prevents accidental complexity, ensures predictable behavior, and keeps the system testable. Persistence adds complexity and must be justified.

### VIII. Traceability (MANDATORY)

Every artifact MUST be traceable back to its source requirement and forward to its implementation.

**Rules**:
- Each task in `tasks.md` MUST reference the plan section it implements
- Each plan section MUST reference the spec requirement it addresses
- Each code file MUST be justified by a task ID
- Changes to any artifact MUST propagate to dependent artifacts
- Use explicit references: `see spec.md#FR-001`, `implements T012`

**Rationale**: Enables impact analysis, prevents orphaned code, facilitates reviews, and maintains integrity across the development lifecycle.

### IX. Mandatory Documentation (NON-NEGOTIABLE)

Documentation is not optional. All projects MUST include:

**Required Documentation**:
- `README.md`: Project setup, dependencies, and usage instructions
- `CLAUDE.md`: Instructions for how Claude Code interacts with this repository
- `specs/<feature>/spec.md`: Feature requirements and acceptance criteria
- `specs/<feature>/plan.md`: Architecture decisions and implementation approach
- `specs/<feature>/tasks.md`: Testable tasks derived from the plan
- `.specify/memory/constitution.md`: This file - project governance

**Rules**:
- Documentation MUST be updated when related artifacts change
- Setup instructions MUST be verified to work from clean state
- All external APIs and contracts MUST be documented
- Breaking changes MUST be documented with migration guides

**Rationale**: Documentation is the contract between specification and implementation. Without it, context is lost, onboarding is impossible, and systems become unmaintainable.

### X. External Knowledge via Context7 (MANDATORY)

When external knowledge, best practices, or library documentation is needed, the Context7 MCP MUST be used explicitly.

**Rules**:
- Do not rely on stale internal knowledge for library APIs or best practices
- Use `mcp__context7__resolve-library-id` followed by `mcp__context7__query-docs`
- Document the library version used in `specs/<feature>/plan.md`
- Verify current patterns and idioms for frameworks via Context7

**Rationale**: Ensures code uses current, correct library patterns. Internal knowledge cutoffs lead to deprecated patterns, security vulnerabilities, and incompatibilities.

## Development Workflow

### Initialization Phase

1. **Constitution First**: Establish project principles (this file)
2. **Feature Request**: User provides natural language feature description
3. **Specification**: Run `/sp.specify` to create `specs/<feature>/spec.md`
4. **Clarification**: Use `/sp.clarify` if specification has gaps

### Planning Phase

1. **Architecture Design**: Run `/sp.plan` to create `specs/<feature>/plan.md`
   - Includes research.md, data-model.md, contracts/, quickstart.md
   - All design artifacts under `specs/<feature>/`
2. **Constitution Check**: Verify plan compliance with all principles
3. **ADR Identification**: Suggest ADRs for architecturally significant decisions
4. **User Approval**: Present plan for human review and approval

### Task Generation Phase

1. **Task Breakdown**: Run `/sp.tasks` to create `specs/<feature>/tasks.md`
   - Organized by user story priority
   - Each task testable and traceable to plan
   - Clear dependencies and parallel opportunities documented
2. **Consistency Analysis**: Run `/sp.analyze` to verify cross-artifact alignment
3. **Task Approval**: Review task list for completeness and correctness

### Implementation Phase

1. **Authorized Execution**: Run `/sp.implement` to execute tasks
   - Only AI may write code
   - Each task maps to specific files
   - Tests written before implementation (if tests requested)
2. **Incremental Commits**: Commit after logical task groups
3. **Validation Gates**: Test each user story independently before proceeding

### Review and Documentation Phase

1. **Constitution Compliance**: Verify all principles followed
2. **Documentation Update**: Ensure README.md and CLAUDE.md are current
3. **Traceability Audit**: Verify all code maps back to tasks and requirements
4. **ADR Creation**: Document significant decisions via `/sp.adr`

## Quality Gates

All projects MUST pass these gates before progression:

### Specification Gate (before planning)

- [ ] All user scenarios have acceptance criteria
- [ ] Functional requirements are specific and testable
- [ ] Success criteria are measurable
- [ ] Ambiguities marked with `[NEEDS CLARIFICATION]`
- [ ] Priorities assigned to user stories (P1, P2, P3...)

### Planning Gate (before task generation)

- [ ] Technology stack documented and justified
- [ ] Project structure defined with concrete paths
- [ ] Constitution Check passes or violations justified
- [ ] Data models documented (if feature involves data)
- [ ] API contracts specified (if feature has external interfaces)
- [ ] Performance and constraint budgets defined

### Task Gate (before implementation)

- [ ] Each task maps to plan section and spec requirement
- [ ] Dependencies explicitly documented
- [ ] Parallel opportunities identified with `[P]` marker
- [ ] File paths are concrete, not placeholders
- [ ] Test tasks included if tests requested
- [ ] User stories organized by priority

### Implementation Gate (during coding)

- [ ] No code written without task authorization
- [ ] All code generated via `/sp.implement` only
- [ ] Clean code principles followed
- [ ] No unauthorized dependencies added
- [ ] State management follows specification
- [ ] Tests written before implementation (if applicable)

### Delivery Gate (before completion)

- [ ] README.md explains setup and usage
- [ ] CLAUDE.md explains repository interaction model
- [ ] All tasks completed or explicitly deferred
- [ ] Each user story independently testable
- [ ] No unresolved `[NEEDS CLARIFICATION]` markers
- [ ] ADRs created for significant decisions
- [ ] Traceability maintained across all artifacts

## Governance

### Amendment Process

This constitution supersedes all other practices and guides. To amend:

1. Propose change with rationale and impact analysis
2. Update constitution version following semantic versioning:
   - **MAJOR**: Backward incompatible principle removals or redefinitions
   - **MINOR**: New principles or materially expanded guidance
   - **PATCH**: Clarifications, wording, typo fixes
3. Create Sync Impact Report documenting template changes required
4. Update all dependent templates and command files
5. Document amendment in git history with clear commit message

### Compliance Review

- All PRs and code reviews MUST verify compliance with this constitution
- Complexity MUST be justified in plan.md "Complexity Tracking" section
- Violations are not permitted unless explicitly approved and documented
- Regular audits ensure traceability and gate adherence
